SECTION 01

Sunrise 是什么

在我们做任何一个具体的 Agent 之前，请先理解 Sunrise 整体是什么，它服务谁，它的"通用性"体现在哪里。

一句话定义：Sunrise 是面向金融/品牌行业内容生产团队的 AI 多 Agent 工作台。它不是单一工具，是一组 Agent 矩阵 + 一套客户专属资产库 + 一套底层合规护栏组成的内容生产基础设施。

关键认知
Sunrise 是多 Agent 平台，每个具体 Agent（KOS 短视频、小红书图文、视频号、公众号…）都是这个平台上的一个"工种 Agent"。它们共享客户资产库、合规规则库、品牌护栏；独立生产路径、产物形态、UI 表达。

三层结构（请记住）

  1. 底座层：客户身份 / 资产库 / 合规规则库 / 共享设计 token / 共享对话组件
  2. Agent 层：KOS 短视频 / 小红书图文 / 视频号 / 公众号 / 客户触达 / 热点中心 / PPT / App 推送 …
    注：合规不是独立 Agent，是「资产·合规」底座的一部分，所有 Agent 共享调用。
  3. 产物层：模板 / 笔记 / 文章 / 话术 / 视频 / 推送（按 Agent 形态各异）

商业前提（务必先知道）

  • 客户类型 1 · 保司：人保、农银人寿、太保 → 项目制采购（150 万级），KOS 短视频是首发 Agent
  • 客户类型 2 · 区域银行：泰隆银行、城商行、农商行 → 培训 + 工具复合采购，小红书图文是首发 Agent
  • 客户类型 3 · 品牌方：贵州中烟、消费品牌 → 项目制内容生产，小红书图文 / 视频号是首发 Agent
  • 不是 SaaS 订阅：保司/银行/品牌方日常发需求给乙方做内容，Sunrise 的价值是"我们就是那个乙方 + 自带 AI 工具链 + 单价更低"，不是卖订阅 license

商业模式
付费方 ≠ 工具用户。Sunrise 的真实使用者大多数情况下是兑吧内容团队（我们自己），替客户做内容。少数场景客户自己用（如银行客户经理做个人 IP）。
所以"谁用"必须区分两层：谁付费（保司/品牌方/银行）、谁打开 Agent（兑吧内容团队 / 个别客户运营）。
UI 上"我" = 工具用户；资产库 = 付费方的资产。两者必须区分清楚，否则产品就做错了。
共性
两个 Agent 在 UI 范式、资产调用方式、角色协作方式、合规呈现方式上完全一致。差异只在「产物形态」和「关键节点序列」—— 这是判断"是不是好 Agent"的核心标准之一：框架一致，节点不同。

SECTION 03

10 条核心设计原则

每条原则后面都给出「为什么」+「具体落地」+「反例」。这是从过去 8+ 版迭代血淋淋打磨出来的，不要绕过。

01

视角永远是「我」第一人称 · 不是甲乙方

用户打开 Agent 时，"我"就是这个内容的生产者。不要在 UI 上出现"客户 / 运营者 / 甲方需求"这类乙方做项目的视角字段。
落地：顶栏右上是"我"的身份（如小草·贵州中烟新媒体运营）；项目条只写"新笔记 · DRAFT" 或"养老金压力 · 需求激发 × 3"。
反例：「客户 = 泰隆银行 / 运营者 = 小张」这种就是把产品做成了乙方项目管理系统。
02

客户资产自动绑定 · 不要做"场景切换器"

真实产品里，登录就已经知道我是谁、我属于哪家客户、我有什么资产。不要在 UI 上做"贵烟 / 泰隆 / 太保"的 demo 切换器——那是 demo 思维。
落地：登录态绑定客户，Agent 自动加载该客户的「产品档案 / 品牌规范 / 合规规则 / 历史爆款 / 账号身份」五类资产。
反例：右上角放一个下拉选客户，每选一个换一套数据 —— 这是给评委看的 demo，不是给用户用的产品。
03

Agent 必须显性引用资产 · 像学术引用

"基于客户画像跑出来"是泛泛话。要在每条 Agent 消息里点名引用："参考你的 产品档案 v2.1 第 3 节"。这才让用户感受到 Agent 真在调用资产而不是瞎编。
落地：消息气泡内嵌"资产引用块"（蓝边框 + 资产名 + 版本 + 引用片段）；右上"已调用 N 份资产"chip 可展开看清单。
反例：只说"根据你的品牌调性…" 但不点名是哪份品牌资产、哪个版本。
04

角色像真实工种 · 不要叫"XX Agent"

用户脑子里的协作对象是"同事"，不是"系统模块"。叫"选题策划 Agent"是 SaaS 厂商腔，叫"编导"才像同事。
落地：两到三字命名 · 像真实工种（编导 / 文案 / 美术 / 合规审核 / 品牌审核 / 业务校准 / 选角导演 / 制作组 / 质检师）。
反例：「选题策划 Agent」「视觉风格 Agent」「提示词工程师 Agent」—— 一眼就知道是工程师起的名，不是用户视角。
05

头像用真 SVG 人物 · 不要首字色块

首字+色块头像让 Agent 看起来像"系统通知者"。圆形真人头像让 Agent 看起来像"同事"。情感连接差异巨大。
落地：复用 docs/Sunrise双屏原型/assets/agents/*.svg（已有 9 个 SVG：小草/编导/文案/业务校准/合规审核/品牌审核/选角导演/制作组/质检师）。新角色用相近 SVG 或新画。
反例：自己生成 <rect+text> 用"选"字+绿底色块当头像，丑且廉价。
06

对话框照搬 KOS · 不要自己生造

KOS 短视频 Agent 的对话布局已经磨了 8+ 版，.bubble / .stream / .compose / .evidence 是磨好的范式。新 Agent 必须复用，不要自己生造组件。
落地：直接 <link rel="stylesheet" href="shared.css">，结构用 .topbar / .rail / .chat / .stream / .bubble / .compose。气泡 = 头像 + .body(.head + .msg) + .evidence。
反例：自己定义 .msg-row .avatar .body .bubble 一套相似但不同的命名，最后跟 KOS 视觉不统一。
07

每条 Agent 消息必须带工具调用证据

没有证据 = Agent 在装饰自己。证据 chip 是 Agent "真的在干活"的视觉锚点。
落地：消息底部 .evidence 区放 .ev / .ev.warn / .ev.risk / .ev.law 椭圆 chip（mono 字体）。例："已读 42 篇爆款"、"禁用词 0"、"广告法 5/5 通过"、"质量 7.4 建议重生"。
反例：Agent 只说"已经帮你跑完选题了"，没有任何可量化的工具痕迹。
08

合规是底线护栏 · 不是主角

合规作为节点存在、作为引用资产存在、作为发布前清单存在，但不要做成"合规雷达占满首页"那种喧宾夺主。
落地：首页合规中心是 1 张卡 + 1 个 rail 入口；Agent 工作流里合规是 1 个节点 + 1 个 Agent 角色；发布前是 1 个清单卡（绿/黄两色）。
反例：首页 1/3 高度用来做合规叙事 / 工作流里合规雷达占全画板。
09

左右联动 · 对话驱动画板状态

对话和画板不是两个独立面板，是一对联动：Agent 说"看右边" → 画板切节点 → 节点上的操作回到对话流。
落地：每条带产物的 Agent 消息底部加 "去看 XXX →" 链接（橙色 mono 字 + 箭头）；点击后画板切到对应节点 + 高亮 + 滚动。
反例：左边只是消息流，右边只是产物展示，互相不知道对方在干什么。
11

全局组件 1:1 复用 · 不要"精简"任何一项

rail / topbar / 用户区 是平台级契约组件，不是页面级装饰。用户在所有 Agent 之间穿梭时，导航的每一项位置必须稳定。任何"当前页面不直接相关，省掉吧"的念头都是错的。
落地：从 屏1-首页.html 或 屏2-KOS·对话工作台-v2.html 把 <header.topbar> + <aside.rail> 字节级拷过来，不增不减不改顺序。仅修改 .ri.active 高亮项 + 用户身份信息。
反例：写 <!-- rail（精简版）-->，省掉"项目""数据"两项。"精简 / 简化 / 省略" 这三个词出现在注释里都是危险信号。
10

数据中性 · 不要厂商自嗨指标

"省人力 ¥4,500 / ROI 5 倍 / 自动化 88%"这种是乙方供应商对甲方做的 PUA 话术，客户一眼识破。
落地：只展示中性事实 ——"本周扫描 412 条"、"红线触发 142 次"、"token 消耗 ¥124.5"、"7 天趋势"。让客户自己得出结论。
反例："我们帮你节省了X 元 / 提升了Y% 效率"—— 加任何形容词都是自嗨。

资产·合规库（每个客户绑定的"我的资产"）

每个客户登录后 Sunrise 自动加载以下 5 类资产，Agent 在工作时显性引用。2026-05-19 起合规与资产已合并在「资产·合规」一个页面管理（旧"合规中心"已 redirect）：

  1. 公司合规手册（带版本号）—— 公司私有的合规红线、行业潜规则、内审规范（区别于平台预置的监管法规）
  2. 品牌手册（带版本号）—— 品牌 VI、话语手册、内容铁律、调性、禁用词、必用元素
  3. 产品资料（带版本号）—— 产品档案、条款、价格、卖点、实拍图、发布会 PPT

  5. Agent 记忆（持续学习）—— 选题采纳偏好 / 文案风格强偏好 / 主角调性 / 合规改写历史

SECTION 05

我们踩过的坑（按类）

下面是从 2026 年 3 月到现在 8+ 版迭代里踩过的真坑。每个坑都附「错误做法 / 正确做法 / 用户原话」三段，方便你判断你正在走的路是不是又掉进去了。

坑 #1 · 视角

把"我打开 Agent"做成了"乙方为客户做项目"

这是最容易反复掉的坑。工程师/AI 默认会把客户名/项目编号/负责人/协作人这些项目管理字段放到顶栏。一放就错。

✗ 错误做法

顶栏「客户 = 泰隆银行 余杭支行 / 运营者 = 小张（综合管理岗）/ 协作人 = X / 项目编号 = P-2026-Q2-007」

✓ 正确做法

顶栏：「小草 · 贵州中烟新媒体运营」（我自己的身份）；项目条：「新笔记 · DRAFT」或「养老金压力 · 需求激发 × 3」（我手头的任务）

用户原话："为什么在这个页面中还出现了客户，运营者，根本不是同一个视角啊"
坑 #2 · 通用性

用"场景切换器"假装通用性 · 实则 demo 思维

当我们说"Agent 是通用的、贵烟泰隆太保都能用"时，工程师/AI 的第一反应是"加个下拉切换 demo 数据"。这是 demo 思维。

✗ 错误做法

右上角放「场景：贵烟 ▾ / 泰隆 / 太保」下拉，切换时整个对话+画板换一套数据。

✓ 正确做法

登录态绑定客户。当前页面只展示当前客户的内容。"通用"体现在「不同客户登录看到的是自己的资产跑出来的自己的内容」，不是 UI 上的切换。

用户原话："为什么要出现场景切换？你直接按照不同客户，都调用客户的资产这样的设定不就好了？"
坑 #3 · 命名

角色叫"XX Agent" · SaaS 厂商腔

"选题策划 Agent / 视觉风格 Agent / 提示词工程师 Agent" —— 这种命名出自工程师视角而不是用户视角。用户脑子里这些是"同事"。

✗ 错误做法

「选题策划 Agent」「文案 Agent」「视觉风格 Agent」「提示词工程师 Agent」「合规 & 平台规则 Agent」

✓ 正确做法

「编导」「文案」「美术」「合规审核」—— 极简两到三字、像真实工种、不带 Agent 后缀。

用户原话："什么叫选题策划 agent，这对吗？你看 kos 那边的角色是怎么描述的呢？"
坑 #4 · 头像

头像用首字色块占位 · 不是真人

偷懒用 <svg><rect><text>选</text></svg> 这种首字色块当头像，整个对话区马上就降级为"系统通知中心"，失去 IM 协作感。

✗ 错误做法

动态生成的"选/文/视/图/规"色块头像。

✓ 正确做法

用 assets/agents/*.svg 里的 9 个真实人物头像（圆形背景+人脸+特征装饰），新角色用相近 SVG 或按风格新画。

用户原话："还是没有头像啊"
坑 #5 · 自嗨数据

厂商自嗨指标 · 客户一眼识破

"省人力 ¥4,500 / ROI 5 倍 / 留痕减负 88%"—— 一看就是甲方 PPT 套路，真客户根本不信。

✗ 错误做法

合规中心右栏放「省人力 ¥4,500 / ROI 5 倍 / Agent 帮你节省 X 小时」

✓ 正确做法

只展示中性事实：「本周扫描 412 条 / 7 天趋势曲线 / 处理分布 4 类 / 红线触发 142 次 TOP3 / token 消耗 ¥124.5」让客户自己得出结论。

用户原话："避险还说得过去，但是省人力和成本都非常的自嗨"
坑 #6 · 商业模式

把 ToB SaaS 思维套在金融行业内容生产上

金融行业（保司/银行）内容生产不是 SaaS 订阅。它们日常就是发需求给乙方做内容。我们要做的不是卖订阅，是"做乙方 + 自带 AI 工具链 + 卖项目"。

✗ 错误做法

设计「月度订阅 / 年度授权」付费墙、按席位计价、按 Agent 用量计费。

✓ 正确做法

项目制：150 万采购给保司做一年的短视频模板包 / 50 万给银行做小红书培训+工具+代运营。客户买的是产物，不是工具。

用户原话："但是作为保司，我的日常就是找服务商下需求，我为什么要自己使用这个平台做呢？"
坑 #7 · 合规喧宾夺主

把合规当主角而不是底线护栏

合规很重要，但不要让它占用首屏 1/3。客户关心的是内容生产本身，合规是 reassurance（让我放心），不是 hero（让我激动）。

✗ 错误做法

首页 1/3 高度做"合规贯穿全流程"叙事 banner / 工作流里合规雷达占满整个画板。

✓ 正确做法

首页合规中心是 1 张 Agent 卡 + 1 个 rail 入口；Agent 工作流里合规是 1 个节点 + 1 个 Agent 角色 + 1 个发布前清单。

用户原话："Sunrise 定位锚点 — 主轴是营销内容生产 agent，合规+品牌一致性做底线护栏不当主角"
坑 #8 · 自己生造组件

不复用 KOS 已经磨好的对话组件 · 自己另起一套

看到要做对话，第一反应是"我自己写 .msg-row .avatar .bubble"。KOS 那边已经磨了 8+ 版 .bubble / .stream / .compose / .evidence，直接拿来用。

✗ 错误做法

在新 Agent 里自己定义 .chat-col / .msg / .body / .text-bubble 一套相似但不同的命名和样式。

✓ 正确做法

<link rel="stylesheet" href="shared.css">，结构直接用 .topbar / .rail / .chat / .stream / .bubble / .compose / .evidence。需要新组件再加，不要替换已有的。

用户原话："对话框你学下 kos短视频的布局呢，现在的布局我根本看不懂"
坑 #9 · Agent 装饰化

Agent 只有头像和名字 · 没有工具调用证据

"AI Agent 帮你跑完了"这种话用户不信。证据 chip是 Agent 真在干活的视觉锚点。

✗ 错误做法

"选题策划 Agent：已经帮你跑完选题了，请查看右侧。" 一句话光秃秃。

✓ 正确做法

消息底部带 .evidence：「已读 42 篇爆款」「禁用词 0/142」「广告法 5/5 通过」「TOP 打分 9.2」
+ 内嵌 .asset-quote：「参考你的「产品档案 v2.1」第 3 节核心卖点」

用户原话：（项目早期）"agent 在为我们工作多少这个很牵强啊"
坑 #13 · 用户身份

把"付费方"当成"工具用户"· 商业模式认知错位

2026-05-19 的最新错误，且是自相矛盾：Section 01 已经写了"保司/银行/品牌方日常发需求给乙方做内容，我们就是那个乙方"，但 Section 02 又写"谁用 = 保司新媒体运营" —— 同一份文档前后打架，因为我没把付费方和工具用户区分清楚。

✗ 错误做法

看到"客户是人保/太保"就以为"工具用户是人保新媒体运营员工"。实际上保司没有/不愿意投入这种人力，真正打开 Agent 在用的是兑吧内容团队（我们自己）。

✓ 正确做法

每个 Agent 必须分两层说清楚：① 付费方（谁掏钱、买什么）② 工具用户（谁打开 Agent、产物给谁用）。UI 上"我" = 工具用户，资产库 = 付费方的资产。

用户原话："这里应该改成，兑吧内容团队，目前来看保司自己没有人力去做这个事"

根本原因：AI 看到 B2B 产品时下意识假设"客户员工 = 工具用户"。这是 SaaS 时代的默认模型，但 Sunrise 是"AI 工具链 + 内容代生产"的复合模式 —— 付费方买的是产物，不是工具席位。
规避机制：① 每个 Agent 卡必须有「付费方 / 工具用户」两行，不能合并成一行"谁用"；② 大多数 Agent 的工具用户是"兑吧内容团队"，少数是客户本人（如银行客户经理做个人 IP / 代理人发朋友圈）；③ 新建 Agent 前先问"这个 Agent 是兑吧打开用，还是客户员工打开用？"，再定 UI。

坑 #12 · 反向入口

建了新 Agent 但没回去把"指向它"的入口接通

这是 2026-05-19 的最新错误。我建好了「屏7-小红书Agent工作台.html」后，去首页改了"小红书图文"卡的 href，但忘了改「屏5-Agent总览.html」里同一张卡的 href。用户从总览页点小红书 → 死链。

✗ 错误做法

新建一个 Agent 后，只在自己常 demo 的页面（首页）改链接，忘了项目里其他指向同一 Agent 的入口。

✓ 正确做法

新建 Agent 后，grep 一遍全项目找所有指向同名 Agent 的卡片入口（首页/总览/资产页/推荐位等），一次性全部接通。

用户原话："agent 的二级页面的小红书也点不进去"

根本原因：思维只覆盖了"用户最常用的入口"，没意识到产品里同一个 Agent 有多个反向入口（首页 Agent 矩阵 / Agent 总览 / 资产页推荐位 / 最近项目卡 / 跨 Agent 跳转…）。
规避机制：① 建完 Agent 跑一条 grep -rn '小红书\|新Agent名' *.html 找出所有提到该 Agent 的位置；② 每处 href="#" 都判断是接通还是改为"规划中"灰态；③ 在 Checklist 第 10 步明确"反向入口扫描"。

坑 #11 · 全局导航

擅自"精简"全局 rail 导航 · 把平台契约当成页面装饰

这是 2026-05-18 在小红书 Agent 上犯的最新错误。rail / topbar / 用户区是平台级全局组件，每个页面必须 1:1 一致，不能基于"当前页面不直接相关"为由省略任何一项。用户在所有 Agent 工作台之间穿梭时，导航的每一项位置都必须稳定。

✗ 错误做法

在新 Agent 页面里写 <!-- rail（精简版）-->，自作主张去掉"项目"和"数据"两项，只保留"首页/Agent/合规/资产/设置" 5 项。

✓ 正确做法

从首页或 KOS-v2 完整拷贝 rail，1:1 不改。完整 7 项：「首页 / Agent / 项目 / 合规 / 资产（div 分隔）/ 数据 / 设置」。

用户原话："这左边的栏也跟首页对不上啊，这种错误为什么会犯，下次如何避免呢"

根本原因：AI 倾向"做得更轻"，但全局一致性 > 单页面视觉精简。"轻"是 reflex，"一致"是契约。
规避机制：① 在新 Agent 起手 Checklist 里加一步「diff 一遍 rail/topbar/用户区，必须与首页字节一致」；② shared.css 旁配套 shared-shell.html 片段作为复制源；③ 任何形如「精简版/简化/省略」的注释都是危险信号，必须重新审视。

坑 #10 · 范围蔓延

把多个 Agent 的能力混在一个工作台里

看到"代理人做同款"就想在 KOS 里嵌入"App 端代理人入口"，看到"出客转化"就想在小红书里嵌入"私信 SOP 编辑器"。克制。每个 Agent 只做它的核心产物，承接由别的 Agent / App 完成。

✗ 错误做法

KOS 短视频 Agent 里加"模拟代理人切素材"演示 / 小红书 Agent 里加"企微 SOP 设计器"

✓ 正确做法

KOS 只产出模板 + 元数据，"代理人做同款"是好保 App 的事；小红书只产出可发布笔记，"出客转化"是另一个 Agent / 已挂载的 SOP 配置项的事。

用户原话："好保 App 端是单一物料部署，不做个性化"
SECTION 06

新 Agent 起手 Checklist

如果你正在启动一个新 Agent（视频号、公众号、客户触达、PPT…），按以下顺序走一遍。每一步都不要跳。

01用一段话说清这个 Agent：谁用（具体职位）、解决什么任务、产出什么形态。说不清就先去对齐，不要写代码。
02列出关键节点序列（5-10 个）。参考 KOS 的 10 节点和小红书的 6 节点。节点是"用户能感知的工作步骤"，不是工程模块。
03列出参与的 Agent 角色（4-7 个）。优先复用 director / copy / art / compliance / brand / qa，避免造新角色。需要新角色就用现有 SVG 风格新画一张。
04列出客户资产（5 类）。这个 Agent 工作时会调用哪些产品档案 / 品牌规范 / 历史数据 / 合规规则 / 账号身份？在画板右上"已调用 N 份资产" chip 显式展出。
05新建文件：docs/Sunrise双屏原型/屏N-XXAgent工作台.html。<link rel="stylesheet" href="shared.css">。骨架直接拷小红书 Agent 的 .topbar / .rail / .chat / .canvas。
5.5⚠️ 全局组件 diff 自检：把新文件的 <header.topbar> 和 <aside.rail> 与 屏1-首页.html diff 一遍。必须字节一致，rail 必须 7 项不能省略。如果出现 <!-- 精简版/简化/省略 --> 注释，立刻删掉重拷。
06写对话流：第一条「我」发起任务 → 系统事件「已加载 X 份资产」 → 每个 Agent 一条，必须带 evidence chip + 资产引用块 + 「去画板看 →」链接。
07写画板节点：每个节点一个 render 函数。节点点击切换画板内容；左侧"去画板看 →"链接联动切节点。
08写产物预览：最后一个节点必须是"最终产物的真实形态预览"（KOS 是上架卡 / 小红书是手机帖子 / 视频号该是横屏视频播放器 / 公众号该是手机长文预览）。
09合规清单：发布前清单卡 5 条（4 绿 + 1 黄软提醒）。规则来自客户资产里的"合规规则库"。
10反向入口全扫描：跑 grep -rn '新Agent名' docs/Sunrise双屏原型/*.html，把所有提到该 Agent 名字的卡片入口的 href="#" 都接通。常见位置：① 首页 Agent 矩阵 ② Agent 总览页 ③ 资产页推荐位 ④ 最近项目卡 ⑤ 跨 Agent 跳转链接。少接一处用户就会点死链一次。
11自测 5 步：① 打开页面无 console error ② 切换所有节点画板都有内容 ③ 点对话里"去画板看 →"能正确切节点 ④ 资产 chip 展开能看清单 ⑤ 最后节点的产物预览不空
12对照本文 10 条原则自查：每条原则都过一遍，确认你没掉进任何坑。
SECTION 07

术语对齐表

下面这些词在我们的语境里有特定的含义，跟通用 SaaS 行业的定义不太一样。沟通时请按这个对齐。

Sunrise平台底座 + Agent 矩阵的整体产品名 · 不是某一个 Agent
兑吧内容团队我们自己（公司内容生产团队）· 大多数 Agent 的真实工具用户。Sunrise 是我们生产内容时用的 AI 工具链
付费方采购我们项目/服务的企业（保司/银行/品牌方）· 不一定是工具用户。付费方买的是产物，不是工具席位
工具用户真正打开 Agent 在用的人 · 大多是兑吧内容团队，少数是客户本人（如银行客户经理做个人 IP、代理人发朋友圈）
KOS 短视频Sunrise 的首发 Agent，面向保司新媒体运营，产物是代理人可一键做同款的短视频模板
小红书图文Sunrise 的第 2 个 Agent，面向行业品牌方 / 账号运营，产物是一篇可直接发布的小红书笔记
好保 App代理人端 App，承接 KOS 产出的模板 · 代理人在这里选模板一键做同款 · 不在 Sunrise 工作台里做
资产客户登录后自动绑定的 5 类内容：产品档案 / 品牌规范 / 历史已发布 / 合规规则库 / 账号身份 · 不是"模板素材"
资产引用块Agent 消息里内嵌的蓝边框引用框，明确点名"这条输出基于哪份资产 / 哪个版本 / 哪个条款"
小草用户的通用化身（"我"的形象）· 不是某一个具体客户公司的员工
节点工作流里的一个可感知工作步骤（如"选题"、"撰写文案"）· 不是工程模块
证据 chipAgent 消息底部的工具调用痕迹（mono 字体椭圆 chip），有 ev / warn / risk / law 四种状态
画板右侧 62% 区域，承载当前节点的可视产物 · 不叫"画布" / "工作区" / "右侧面板"
客户采购我们项目的企业（人保、农银人寿、贵州中烟、泰隆银行）· 不出现在产品 UI 里，只在登录态绑定身份
项目制客户一次性采购一个项目（如 150 万一年的短视频模板包），不是 SaaS 订阅
SECTION 08

给 AI Agent 的特别说明

如果你正在用 Claude Code / Cursor / 其它 AI 协作工具做 Sunrise 的 Agent，请把下面这段读进上下文。

FOR AI
本项目不是普通的 SaaS 原型。它是面向特定 B 端客户的项目制内容生产工具。请禁用以下默认行为：
① 不要主动加"客户 / 项目编号 / 协作人"等项目管理字段到 UI
② 不要为不同客户做"场景切换器"，客户身份由登录态绑定
③ 不要把任何角色命名为"XX Agent / XX 助手 / XX Bot"，用"编导 / 文案 / 美术"这种工种名
④ 不要用首字色块当头像，用 assets/agents/*.svg 里的真人头像
⑤ 不要自己生造对话组件，用 shared.css 已有的 .bubble / .compose / .evidence
⑥ 不要用"省人力 / ROI / 提升效率"这类自嗨指标，只用中性事实
⑦ 不要把合规放在 hero 位置，它是底线护栏不是主角
⑧ 不要把多个 Agent 的能力混在一个工作台里（克制范围）
⑨ 不要"精简"全局 rail / topbar / user-chip，必须从已建页面字节级 1:1 拷贝。任何"精简版/简化版"注释都是危险信号。
⑩ 建完新 Agent 后必须 grep 全项目找所有提到该 Agent 的入口，一次性接通。"反向入口"思维：不只是改你刚才打开的页面，是改所有指向新 Agent 的地方。
⑪ 不要把"付费方"当成"工具用户"。Sunrise 大多数 Agent 的工具用户是兑吧内容团队（我们自己），不是保司/品牌方员工。新 Agent 必须分两层说清「付费方」和「工具用户」，不能合并成一行"谁用"。

给 AI 的工作流建议

  1. 开工前先读完本文档（尤其 Section 03 / 05 / 06）
  2. 读完后用一句话向用户复述："我理解这次要做的是 [X Agent]，付费方是 [P]、工具用户是 [U]（必须区分两层），产物是 [Z 形态]，节点是 [N1→N2→…→Nn]，会用到的 Agent 角色是 [A1, A2, …]，会调用的资产是 [R1, R2, …]。"
  3. 用户确认后再写代码
  4. 写完后对照 Section 06 的 12 步 Checklist 自查
  5. 把自查结果发给用户，让他点页面看（启动 python3 -m http.server）

常见误判 · AI 容易做错的事

  • "用户没说要 XX 但应该有" → 多数情况是 AI 自己脑补的。先问，再做。
  • "做一个 demo 切换器方便演示" → 99% 是错的。客户身份由登录态绑定。
  • "加个数据看板显示生产效率" → 大概率是自嗨指标。问清楚要展示什么中性事实。
  • "为每个客户单独做一份 UI" → 错。同一份 UI，资产不同。
